Dos filosofias de generacion

v1 Estatico (Clasico)

  • El curso se genera una vez, completo
  • Mismo contenido para todos los alumnos
  • Modulos → lecciones → ejercicios, todo de golpe
  • Pipeline LangGraph asincrono con SSE
  • Resultado: contenido Markdown + ejercicios JSON en BD
  • El admin puede editar las lecciones despues
  • Revision de calidad automatica con LLM
  • Hasta 2 ciclos de refinamiento
  • Tiempo total: 10-30 segundos

v2 Dinamico (Personalizado)

  • El contenido se genera por nodo, por alumno, bajo demanda
  • Cada alumno recibe contenido adaptado a su perfil
  • En design-time solo se crea el esquema (nodos + requisitos)
  • En runtime, cuando el alumno llega a un nodo, se genera su contenido
  • Resultado: programa UI en dialecto canonico (no Markdown)
  • Cache por cache_key (perfil + schema_version + modelo + ...)
  • Validacion de programa + retry + fallback a v1
  • Tiempo por nodo: 2-5 segundos
La decision es por curso. Un curso con delivery_mode='dynamic' Y schema_status='validated' se sirve por v2. Cualquier otro se sirve por v1. El punto de decision unico: course_delivery.resolve_delivery().

Prerequisito: preparar el documento fuente
API POST /documents (upload)

El admin sube un PDF, DOCX, MD o TXT. Se guarda el archivo y se crea un registro en documents con status "uploaded".
API POST /documents/{id}/process
src/services/document_service.py
Procesa el documento en background:
  1. Parsea el archivo (PDF → texto, DOCX → texto, etc.)
  2. Extrae full_text (el documento completo como string)
  3. Si tiene mas de 5 paginas: lo trocea en chunks semanticos
  4. Si hay un proveedor de embeddings: genera vectores para cada chunk
  5. Guarda chunks en document_chunks (con vector en pgvector)
  6. Marca el documento como "ready"
Resultado
El documento esta listo. Hay dos modos de RAG posibles segun el tamano:

≤ 5 paginas: full_text

  • Se pasa el texto completo al LLM como contexto
  • Mas preciso, cero latencia de busqueda

> 5 paginas: chunked

  • Busqueda semantica por modulo (top K=15)
  • Solo los chunks relevantes van al LLM

Un LLM independiente revisa la calidad del contenido generado.

LLM Llamada de revision

Criterios 1. Precision (hechos verificables contra fuente)
2. Completitud (temas clave cubiertos)
3. Sin artefactos de cita ([Fuente: ...])
4. Calidad de ejercicios (respuestas correctas)
5. Alineamiento Bloom (≥50% apply+)
6. Lenguaje claro y profesional
7. Consistencia entre modulos
Salida{"passed": bool, "overall_score": 0-1, "issues": [{"severity", "module_index", "description", "suggestion"}]}
Resiliente. Si el LLM de revision falla (rate limit, proveedor caido), el pipeline NO se rompe. Marca review_skipped: true y sigue adelante. Razon: la revision es la 5a llamada LLM; un fallo no deberia descartar todo el trabajo. El admin aun tiene que publicar manualmente.

Fase 3: Evaluacion y mastery

src/routes/nodes.py:652-850+
El alumno responde a los ejercicios del nodo.

Flujo de evaluacion

  1. Recupera la answer_key del render (nunca estuvo en el browser)
  2. grade_item(): evalua cada respuesta contra la clave
  3. Devuelve: score, explicacion, resultados por item
  4. transition_on_answer(): actualiza mastery con modelo bayesiano
  5. Detecta transiciones de estado: not_started → learning → mastered
  6. Si mastered: incrementa nodes_completed, actualiza format_vector
  7. Cierra el nodo
